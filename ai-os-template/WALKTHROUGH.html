AI Engineering OS — Walkthrough

Template v0.3 · Routing rebalance 2026-07-13 · Source of truth: ai-os-template/DESIGN-MEMO.md and routing/model-routing.md

This is a guided read of the AI Engineering OS: what each component owns, how a task moves through the system, which model works each phase, and what happens when a provider runs out of quota.

How the callouts work

Amber marks an architectural judgment. Green marks merged or deduped content. Red marks a decision or route that needs attention. Every label is written out, so color is never the only signal.

Read straight through for the operating model, or jump to §8 and change provider availability in the routing lab to see the fallback logic execute.

2 · The core idea

The OS packages seven things into one reusable template that gets instantiated into real repos:

  1. Root instruction files (AGENTS.md, CLAUDE.md)
  2. Repo-resident docs/memory system
  3. Workflow specs
  4. Hook specs (Claude Code events)
  5. Slash command specs
  6. Subagent role definitions
  7. Model routing rubric

The design targets four recurring failure modes: repeated context loss, low-quality agent behavior, missed verification, and inconsistent planning. Everything downstream should be traceable to one of those four.

Six principles the template is built on

PrincipleWhat it means in practice
Concrete abstractionEvery recommendation maps to a file, hook, command, workflow, skill, agent, routing rule, verification gate, or convention. Nothing ships as advice-only.
Delegate for leverageThe current session owns coherent work. Delegate only independent slices where parallel speedup, mechanical volume, or fresh context outweighs coordination cost.
Repo-resident memoryModels forget; the repo persists. Everything an agent needs is in the repo or explicitly mapped from it.
Proportional ceremonyThe solo path is lighter than a production-team path, but never below the floor of inspect before edit, plan proportional to risk, run verification, and leave a clean handoff.
Merge, don't bulldozeInstantiation adapts to a repo's existing conventions via a manifest. The template never silently overwrites or renames what a repo already has.
Codex-first, harness-portableHarness-neutral content lives in AGENTS.md. A thin CLAUDE.md adapter exposes subscription-backed Fable and Sonnet lanes without making Claude the control plane.

Judgment · #A1

The packet phrased memory as "on disk" and left worktree scope open. I bound it to three tiers: shared durable docs (in the repo), task-scoped disposable docs (dev/active/<task>/), and worktree-local logs (never durable). This is what prevents worktree-cleanup from erasing project memory and what stops task docs from polluting SPEC.md.

Anti-drift and anti-churn — the two rules that make this work

Anti-drift: plans live in task docs; decisions get promoted to global docs. Never the reverse. PROJECT-STATUS.md holds only the current handoff.

Anti-churn (for automatic doc writes): updates fire at checkpoints, not per response; a significance check gates each write; status files are idempotent overwrites so noise cannot accumulate; every automatic edit records a one-line reason.

Judgment · #A2 — the AGENTS/CLAUDE split

The packet asked whether AGENTS.md and CLAUDE.md should be mirrors, layered, or harness-siblings. I chose layered: AGENTS.md is canonical + harness-neutral (behavior rules, doc map, workflows, standards); CLAUDE.md is a thin adapter (slash commands, hooks, Claude-specific routing) that starts with @AGENTS.md. No generation step. Reason: mirrors drift, generation adds a build step. This matches how the lower-db overlay already works, so both instances land consistently.

Judgment · #A3 — three write tiers

The packet said "hooks should auto-edit docs" but flagged noisy churn as a risk. I split doc-editing authority into Tier A (fully automatic — status, changelog draft, tool cache), Tier B (guarded automatic — SPEC.md, docs/ — only stable facts + recorded reason), Tier C (staged review — skills, root instructions, hooks). This is how the same principle can produce "aggressive auto-updates on status" and "never silently edit a skill."

5 · Workflow backbone

Eleven workflow specs in workflows/. Each has exactly seven sections: Trigger, Inputs, Steps, Output contract, Verification, Ceremony scaling, Failure handling. Steps name the actor (orchestrator vs which subagent role vs hook).

debugComplete evidence sweep → root-cause register → one fix batch → focused reproduction → one warranted broad gate./debug-mode

Experimentation is a first-class methodology and the routing matrix's evidence engine.

Judgment · #A4 — smallest useful planning artifact

The original accelerated grill created planning work even when intent was already clear. Routing v0.9 keeps one breadth-first uncertainty sweep, asks only questions that materially change behavior or a difficult-to-reverse choice, and produces only the artifact a downstream consumer needs.

6 · Quality system — complexity tiers and audit lenses

Tasks are classified by actual consequence, ambiguity, and reversibility. File count and user-facing scope do not create process by themselves.

TierLooks likePlanAuditReview
SimpleLocalized, known, easily reversible.Inline intentNone by defaultSelf-review
MediumBounded new behavior with clear intent and cheap rollback.Inline checklistNone by defaultSelf-review; add one independent pass only for real uncertainty
HighActually changes authority, destructive/external effects, irreversible contracts, or similarly costly recovery.Plan + rollbackOne breadth-first risk inventoryOne independent reviewer + concrete concurrent specialists

Promotion rule: name the concrete irreversible or high-consequence behavior. A sensitive-path label, multiple files, cross-repo work, or “user-facing” does not promote by itself.

Throughput rule: finish breadth-first discovery, implement one batch, use focused checks, fan in review when warranted, then run one broad gate at the stable boundary.

7 · Contracts — the four rules everything else depends on

7.1 · Delegation contract

Delegate only when leverage exceeds coordination cost. A routine task needs goal · scope · exclusions · expected result · verification · stop condition. Proof-required, external, or experimental work adds heavier provenance only when needed.

Subagents may not: perform unbounded repo-wide rewrites, make irreversible external changes without permission, touch secrets, self-approve their own work, or substitute passing tests for understanding.

7.2 · Return packet

A routine result contains findings or changes · verification · risks · next action. Do not create an output artifact that nobody will use.

7.3 · Hook classification

ClassUsesGuidance
BlockingSecrets exposure, client-side API keys, destructive git ops without permissionSparse. Hooks never create a requirement to run an expensive check.
AdvisoryMissing docs/tests consideration, error-handling reminders, architecture concernsNotice; agent decides.
DelegatingExplicit High-risk/proof review onlyDisabled by default; size/frontend/docs changes alone never hand off.
Automatic maintenancePROJECT-STATUS.md, changelog draft, tool cache, generated docsFire at checkpoints; significance-gated; anti-churn rules apply.
Judgment · #A5 — blocking hooks conservatively scoped

Blocking remains limited to secrets, client-side provider keys, and destructive git without permission. Verification is one advisory at the stable batch boundary; dirty trees, large diffs, frontend changes, and type-error counts do not auto-delegate or create review gates.

7.4 · Doc write tiers

See §4 above. This is the same rule set expressed as write authority — Tier A auto, Tier B guarded, Tier C staged.

    Fable ROI gate

    Fable is used when the decision is durable or expensive to reverse, a compact review packet is possible, an outside critique could change the decision, and the result will be recorded for reuse. High-return uses include architecture boundaries, migrations and rollback plans, harness policy, conflicting-review adjudication, and rare flagship positioning critique after Sonnet drafts the copy.

    The budget rule is one critique and, only when needed, one focused follow-up. No Fable swarms. Routine orchestration, implementation, code review, status, summaries, copy drafting, and repeated review stay off Fable. Medium or High complexity alone is not an escalation trigger.

    Local subscription route

    When a High-risk cross-family review is warranted, Codex can invoke claude -p --model claude-opus-5; the exceptional architecture lane uses claude -p --model fable. The route must preflight auth and be treated as unavailable where separate Claude authentication is absent.

    What you should see while work runs

    1. Start. Task tier, chosen route, reason, and next observable checkpoint.
    2. Phase boundary. Completed artifact or evidence path, next owner, and any unverified work.
    3. Failure. Exact route and error classification. A failed command is never called “still running.”
    4. Takeover. Fallback route, preserved checkpoint, unchanged acceptance checks, and any reduction in review diversity.
    5. Finish. Implementer, reviewers, verification, skipped checks, fallback ledger, and residual risk.

    GLM rule: the installed experimental route must stream, emit content-free heartbeats, save partial checkpoints, and stop at ten minutes. One transient failure may retry from the last checkpoint; timeout, quota, or auth failure moves the unchanged packet to Composer, then Terra.

    11 · Instantiation — how a template becomes a live repo instance

    Every instantiated repo gets docs/ai-os-manifest.md. Schema and full checklist in ai-os-template/instances/MANIFEST-SCHEMA.md. Summary of the procedure:

    1. Codex recon packet: stack, verification commands, existing doc roles, conventions, collision risks.
    2. Codex Sol High makes binding decisions; anything unresolvable goes to you.
    3. Isolated worktree, branch codex/ai-os-instance off origin/main — never the (possibly dirty) root checkout.
    4. Codex writes bound files per packet; no git ops, no deletions, no renames; existing marker blocks preserved byte-identical.
    5. Shared specs are vendored or resolved through AI_OS_HOME plus a portable source URL. Author-specific absolute checkout paths are forbidden, and root-doc summaries remain usable without the optional shared checkout.
    6. Codex Sol High inspects the diff, verifies no unresolved template-binding markers or host-specific paths survive, checks the fallback with AI_OS_HOME unset, and commits by named file.
    7. Promote repo learnings to the template only when they generalize.
