AI Engineering OS — Walkthrough

Template v0.2 · Built 2026-07-08 · Revised 2026-07-12 after Jake's review · Source of truth: ai-os-template/DESIGN-MEMO.md

This is a guided read of the AI Engineering OS: what each component is, how it works alone, and how the pieces compose. Judgment calls I made without asking are flagged, deduped content is called out, and pending decisions are collected in §13.

How the callouts work

Amber = a judgment call I made without pausing to ask (based on the packet, existing repos, or design principles). Green = content I merged/deduped instead of preserving multiple copies. Red = a decision that still needs you.

You can read straight through, or jump to §13 first to see what still needs you, then read the rest for context.

2 · The core idea

The OS packages seven things into one reusable template that gets instantiated into real repos:

  1. Root instruction files (AGENTS.md, CLAUDE.md)
  2. Repo-resident docs/memory system
  3. Workflow specs
  4. Hook specs (Claude Code events)
  5. Slash command specs
  6. Subagent role definitions
  7. Model routing rubric

The design targets four recurring failure modes: repeated context loss, low-quality agent behavior, missed verification, and inconsistent planning. Everything downstream should be traceable to one of those four.

Six principles the template is built on

PrincipleWhat it means in practice
Concrete abstractionEvery recommendation maps to a file, hook, command, workflow, skill, agent, routing rule, verification gate, or convention. Nothing ships as advice-only.
Orchestrator, not laborerFable owns framing, judgment, synthesis. Codex + cheaper models do research, drafting, mechanical implementation, verification, doc maintenance under bounded contracts.
Repo-resident memoryModels forget; the repo persists. Everything an agent needs is in the repo or explicitly mapped from it.
Proportional ceremonySolo path lighter than a production-team path — but never below the floor of inspect-before-edit, plan-proportional-to-risk, run verification, leave clean handoff.
Merge, don't bulldozeInstantiation adapts to a repo's existing conventions via a manifest. The template never silently overwrites or renames what a repo already has.
Claude/Fable-first, Codex-portableHarness-neutral content in AGENTS.md (Codex reads that natively); Claude-specific mechanics in a thin CLAUDE.md adapter.

The operating loop has six elements. Each is a concrete artifact somewhere in the template:

Judgment · #A1

The packet phrased memory as "on disk" and left worktree scope open. I bound it to three tiers: shared durable docs (in the repo), task-scoped disposable docs (dev/active/<task>/), and worktree-local logs (never durable). This is what prevents worktree-cleanup from erasing project memory and what stops task docs from polluting SPEC.md.

Six layers, each with a clearly-scoped write authority. The tier tells you (and hooks and agents) who is allowed to edit it and how often.

Anti-drift and anti-churn — the two rules that make this work

Anti-drift: plans live in task docs; decisions get promoted to global docs. Never the reverse. PROJECT-STATUS.md holds only the current handoff.

Anti-churn (for automatic doc writes): updates fire at checkpoints, not per response; a significance check gates each write; status files are idempotent overwrites so noise cannot accumulate; every automatic edit records a one-line reason.

Judgment · #A2 — the AGENTS/CLAUDE split

The packet asked whether AGENTS.md and CLAUDE.md should be mirrors, layered, or harness-siblings. I chose layered: AGENTS.md is canonical + harness-neutral (behavior rules, doc map, workflows, standards); CLAUDE.md is a thin adapter (slash commands, hooks, Claude-specific routing) that starts with @AGENTS.md. No generation step. Reason: mirrors drift, generation adds a build step. This matches how the lower-db overlay already works, so both instances land consistently.

Judgment · #A3 — three write tiers

The packet said "hooks should auto-edit docs" but flagged noisy churn as a risk. I split doc-editing authority into Tier A (fully automatic — status, changelog draft, tool cache), Tier B (guarded automatic — SPEC.md, docs/ — only stable facts + recorded reason), Tier C (staged review — skills, root instructions, hooks). This is how the same principle can produce "aggressive auto-updates on status" and "never silently edit a skill."

Judgment · #A4 — accelerated grill

The packet said "possible pattern: 5 questions with user, 20 self-questions, then review." I codified that as the spec workflow's step 4–5 and made options-considered + selected-option rationale required for each self-grill question. The user only gets asked when answers would materially change the plan. This is the primary way solo work stays disciplined without the full team-production grill.

6 · Quality system — complexity tiers and audit lenses

Every non-trivial task is classified before starting. The tier drives planning depth, audit lenses, review independence, and model routing.

TierLooks likePlanAuditReview
SimpleSingle file, known pattern, easily reversible, no data/security surface.Inline intentOne combined pass (adversarial+steelman+neutral baked in)Self-review OK
MediumMulti-file, new behavior, or user-facing.Written plan in task docsThree lens passes by one auditor subagentReviewer independent of implementer
HighArchitecture, auth/security/payments/data migration, cross-repo, low reversibility.Full plan + rollbackThree independent lens subagents; orchestrator synthesizesIndependent reviewer + specialist lenses

Promotion rule: a single High on risk, reversibility, or blast radius makes the task High regardless of size. When in doubt between tiers, take the higher one — the extra ceremony is one audit pass, not a process tax.

Review independence is the non-negotiable core: the coding agent is never the sole reviewer of its own work. This is what most of the routing and delegation rules are protecting.

7 · Contracts — the four rules everything else depends on

7.1 · Delegation contract

Every subagent task must specify: goal · repo/paths · files to inspect · excluded areas · expected output artifact · allowed tools · model preference · verification requirement · quality bar · stop condition. If you can't write those ten, you're not ready to delegate.

Subagents may not: perform unbounded repo-wide rewrites, make irreversible external changes without permission, touch secrets, self-approve their own work, or substitute passing tests for understanding.

7.2 · Return packet

Every subagent result must contain: task assigned · files/docs inspected · facts found · decisions made · output artifact or patch summary · verification run · risks · open questions · recommended next action. Concise packet, not a transcript.

7.3 · Hook classification

ClassUsesGuidance
BlockingSecrets exposure, client-side API keys, destructive git ops without permission, failed build/typecheck on code changesSparse. Documented local override for non-production work.
AdvisoryMissing docs/tests consideration, error-handling reminders, architecture concernsNotice; agent decides.
DelegatingType errors → fix-types; large diff → architecture reviewer; frontend diff → UX reviewer; docs drift → doc maintainerHand off instead of pushing through.
Automatic maintenancePROJECT-STATUS.md, changelog draft, tool cache, generated docsFire at checkpoints; significance-gated; anti-churn rules apply.
Judgment · #A5 — blocking hooks conservatively scoped

The packet said "aggressive blocking hooks are frustrating." I limited blocking to four cases: secrets exposure, client-side model API keys, destructive git ops on the main branch without in-conversation permission, and failed build/typecheck on code changes. Everything softer (type-error volume, large diff, missing tests) becomes delegating or advisory. The blocking-hook override convention is documented so local non-production work isn't gated by a hook you'd have to fight.

7.4 · Doc write tiers

See §4 above. This is the same rule set expressed as write authority — Tier A auto, Tier B guarded, Tier C staged.

The matrix in routing/model-routing.md separates verified routes from work that is decided but not yet built or verified. It is date-stamped and versioned because model quality and pricing change.

11 · Instantiation — how a template becomes a live repo instance

Every instantiated repo gets docs/ai-os-manifest.md. Schema and full checklist in ai-os-template/instances/MANIFEST-SCHEMA.md. Summary of the procedure:

  1. Codex recon packet: stack, verification commands, existing doc roles, conventions, collision risks.
  2. Fable makes binding decisions; anything unresolvable goes to you.
  3. Isolated worktree, branch codex/ai-os-instance off origin/main — never the (possibly dirty) root checkout.
  4. Codex writes bound files per packet; no git ops, no deletions, no renames; existing marker blocks preserved byte-identical.
  5. Fable inspects the diff, verifies no unresolved template-binding markers survive, commits by named file.
  6. Promote repo learnings to the template only when they generalize.
